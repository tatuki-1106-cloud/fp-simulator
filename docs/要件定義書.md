## 1. 背景と目的

### 1.1 背景

「人生100年時代」「新NISAの開始」「物価上昇」などを背景に、個人が自身のライフプラン(生涯キャッシュフロー)を正確に把握する必要性が高まっている。既存の高精度ライフプランソフト(FP-UNIV等)は優秀だが、以下の課題がある。

- クローズドなSaaSであり、APIが提供されない
- 計算結果をAIエージェント(Claude等)から直接参照・操作できない
- 自分の制度理解・仮説に基づくカスタマイズ(パラメータ変更、将来の税制改正シナリオ等)ができない

### 1.2 目的

1. **FP-UNIVが提供する機能(税制・社会保障制度に忠実な月次キャッシュフローシミュレーション)を自力で再現**する
2. その上に、FP-UNIVにはない **MCP(Model Context Protocol)サーバー機能** を持たせ、AIエージェントがライフプランの計算・参照・更新・説明をツールとして実行できるようにする
3. **税制・制度改正に強い設計**(数値変更はパラメータ編集のみで対応可能)を実現し、長期的に自分で保守し続けられるシステムにする

### 1.3 開発哲学(FP-UNIVの思想を継承)

- **係数の恣意調整をしない**:物価上昇率・給与上昇率・運用利回りのデフォルトは 0%。前提条件はすべてユーザーが可視化・変更可能
- **統計の平均値で画一化しない**:個人の詳細情報を入力して個別計算する
- **法令に忠実**:税率・控除額・社会保険料率はすべて根拠法令への出典付きで管理する

## 2. 参考システム(FP-UNIV)分析サマリ

調査レポート全文は `files/fp-univ-research.md`(セッションアーティファクト)に保存。要点のみ抜粋。

### 2.1 FP-UNIVのコア特徴

| 特徴 | 内容 |
|---|---|
| 計算粒度 | **1ヶ月単位**のキャッシュフロー計算(税・年金・社保の精度の源泉) |
| 年金計算 | ねんきん定期便入力対応、繰上/繰下、在職老齢年金、遺族・障害年金、併給調整の自動最適化。日本年金機構の試算に最も近いと主張 |
| 税・社保 | 所得税(年末調整還付は12月反映)、住民税(翌年6月〜)、厚生年金・健康保険・介護保険・雇用保険を標準報酬月額ベースで自動計算 |
| 住宅ローン | 元利/元金均等、変動金利の5年/125%ルール、繰上返済、住宅ローン控除の「実際値」計算 |
| 万が一 | 「生きる道/世帯主死亡/配偶者死亡」3パターン同時作成、必要保障額分析 |
| その他 | iDeCo/企業型DC/NISA、教育費、産休育休、児童手当、不動産投資分析、モンテカルロ、提案書PDF、プラン比較 |
| 入力形式 | Q1〜Q11のウィザード形式(家族/収入/年金/生活費/教育費/住まい/乗り物/ローン/保険/貯蓄運用) |
| 法令改正対応 | クラウド型で自動反映 |

### 2.2 本システムのポジショニング

FP-UNIVの**再発明ではなく「AIネイティブな再構築」**。機能面はコア部分から追いつき、MCPによるAI連携・パラメータの透明性・仮説シミュレーションで差別化する。

### 2.3 実サイトUI確認結果(2026-08-13)

実際の画面(無料プランでログインして確認)から得られた、要件定義に影響する知見:

#### 入力ウィザード(Q1〜Q11)

| Q | 実際の構造 | 要件への反映 |
|---|---|---|
| Q1 家族 | 世帯主/配偶者/子/その他。**想定寿命と「万が一年齢」を別々に入力**。障害区分(身体・精神1級等)、配偶者は結婚記念日、子は「世帯主と生計を一にする期間」(生涯/最終学歴にあわせる/期間指定) | 家族モデルに `想定寿命` `障害等級` `扶養期間` を持たせる。「万が一」は将来拡張 |
| Q2 収入 | 収入種別は **「給与(厚生年金)/役員報酬(厚生年金)/役員報酬(国民年金・国保)/給与(国民年金・国保)」の4区分**で、社保の種別を直接選ばせる設計。期間・月額・賞与(月指定・複数回)・年間上昇率(「上昇率を逆算」ボタンあり)。**扶養設定**(なし/期間と扶養者を指定)。**産休育休設定**(産後パパ育休/産前産後休業/育児休業を日付範囲で指定、「取得可能全期間」プリセットあり) | MVPの収入種別はこの4区分モデルを採用(自営業の別種別は将来拡張)。賞与は月指定・複数回に対応 |
| Q3 年金 | 「加入実績から自動計算/直接指定」の選択式。加入期間・見込額・「最近の月別状況」。「他の家族の死亡による年金」(遺族年金の受給設定)。付加年金・国民年金基金 | MVPは「加入実績から自動計算」と「直接指定」の両対応 |
| Q4 生活費 | **物価上昇率の入力が生活費画面の冒頭にある**(デフォルト0.5%と表示。FP-UNIVは実際には0%以外も提示)。支出は「スケジュール(期間)/内容/周期(月ごと等)/金額/万が一時の金額/上昇率」の表形式 | 前提条件のデフォルト値は要再検討(§15 U6参照。ただし決定済み:プリセットは出典付きで用意) |
| Q8 ライフイベント | 「摘要/タイプ/実施期間/周期/一回当たりの金額/万が一時の金額」の汎用イベント+「結婚援助」「葬儀費」の専用フォーム | MVPは「イベント的支出」として生活費設定に含める(汎用イベントモデル) |
| Q6 住まい | 賃貸(賃料/敷金/礼金/仲介手数料/更新)と所有(物件別)を分離 | MVPは対象外(将来拡張)。ただし賃貸の家賃は生活費で代替可能とする |
| Q9 ローン | 「ローン(住宅・自動車・教育など)」と「奨学金」の2系統。金利タイプ/時期/返済額/手数料。「ローン分析」へのリンク | 将来拡張フェーズ1 |
| Q11 貯蓄・投資 | 現金/銀行預金(単利%)/証券口座(課税口座・NISA等)/iDeCo/DC/小規模共済。**月初残高基準**で入力(「2026年10月月初時点での残高」)。外貨建ては開発中と明記 | MVPは「現金+預金口座(残高・金利)」のみ。月初残高基準の考え方を採用 |

- **「生きる道/世帯主万が一/配偶者万が一」の3タブが結果画面上部にある**(現状は対象者・万が一年齢を指定して比較)

- **有価証券マスターデータ**の管理機能がある(将来の証券口座対応で参考)

## 3. ヒアリング決定事項

| # | 事項 | 決定内容 |
|---|---|---|
| D1 | 対象ユーザー | 自分+家族/友人など**少数の身内向け** |
| D2 | プラットフォーム | **Google Cloud Run** 上のWebアプリ(懸念点は §11.3 に記載) |
| D3 | 技術スタック | **Python (FastAPI + Jinja/HTMX)** |
| D4 | MCPの方向性 | **アプリ自体がMCPサーバーになる**(AIがライフプラン計算・参照・更新をツールとして呼ぶ) |
| D5 | MVPスコープ | **コアから段階的**(家族・収入・生活費・年金・税/社保のキャッシュフロー表 → ローン等は後から拡張) |
| D6 | 計算粒度 | **月単位**(FP-UNIV同等の精度を目指す) |
| D7 | 税制変更耐性 | **方式A: OpenFisca式**(YAMLパラメータ時系列管理 + 純粋関数エンジン + 出典必須 + 回帰テスト) |
| D8 | 認証 | **Google IAP**(Identity-Aware Proxy) |
| D9 | シナリオ | MVPは「生きる道」1パターンのみ(万が一・比較・モンテカルロは将来拡張) |
| D10 | データベース | **SQLite + Litestream**(GCSへ自動バックアップ、Cloud Runは max-instances=1) |

## 4. スコープ

### 4.1 MVP(フェーズ1)

#### 入力

| 機能 | 内容 |
|---|---|
| 家族設定 | 世帯主・配偶者・子(生年月日、続柄、性別、**想定寿命**、**障害等級**、**世帯主と生計を一にする期間**(生涯/最終学歴にあわせる/期間指定)、扶養判定に必要な属性) |
| 収入設定 | 給与収入(額面月収・賞与(月指定・複数回)・上昇率・期間)、退職金(勤続年数・額面)、その他収入。収入種別は **「給与(厚生年金)/役員報酬(厚生年金)/役員報酬(国民年金・国保)/給与(国民年金・国保)」の4区分**(社保種別を直接指定、FP-UNIVのモデルに準拠)。※MVPは会社員/公務員のみ、自営業は将来拡張 |
| 年金設定 | 国民年金/厚生年金の加入実績(加入月数・平均標準報酬額)、受給開始年齢(繰上/繰下)。**「加入実績から自動計算」と「直接指定(金額入力)」の両方**に対応(FP-UNIV準拠) |
| 生活費設定 | 月額基本生活費、イベント的支出(旅行・買替等の単発/周期支出) |
| 資産設定 | 現預金口座(**月初残高**・金利)。証券口座・運用はMVPでは金利0の口座として扱う |

#### 計算

| 機能 | 内容 |
|---|---|
| 月次キャッシュフロー | 収入−支出−税−社会保険料を月単位で積算 |
| 所得税 | 給与所得控除、基礎控除、配偶者控除/扶養控除、社会保険料控除。源泉徴収+年末調整(12月還付/追徴)相当の月次モデル |
| 住民税 | 前年所得課税、翌年6月〜翌々年5月の徴収サイクル |
| 社会保険料 | 標準報酬月額テーブルに基づく厚生年金・健康保険(協会けんぽ・**都道府県別料率**)・介護保険(40〜64歳)・雇用保険。年度改定(4月/9月等)の時期を反映 |
| 公的年金 | 老齢基礎年金・老齢厚生年金(報酬比例部分+定額部分)、経過的加算、加給年金、繰上/繰下の増減額。**再評価率は最新値を将来分にも適用**(日本年金機構と同方式) |
| 退職金 | 退職所得控除、1/2課税、分離課税の自動計算 |

#### 出力

| 機能 | 内容 |
|---|---|
| キャッシュフロー表 | 月次(年次サマリ表示+月次ドリルダウン) |
| 貯蓄残高グラフ | 現預金残高の生涯推移 |
| サマリー | 生涯収支、**最低貯蓄残高とその発生月**、**最終残高**、残高がマイナスになる時期の警告(FP-UNIVのサマリー構成を参考に、「イベント実現率」はMVPでは省略) |

#### 基盤

| 機能 | 内容 |
|---|---|
| 税制パラメータ管理 | YAMLによる時系列パラメータ(§9) |
| MCPサーバー | AIからの参照・計算実行(§7.5) |
| 認証 | IAP によるアクセス制限 |
| 永続化 | SQLite + Litestream バックアップ |

### 4.2 将来拡張(フェーズ2以降)

優先度順(目安):

1. **住宅ローン**(元利/元金均等、変動金利5年/125%ルール、繰上返済、住宅ローン控除の実際値計算)
2. **教育費**(子ごとの学校種別・期間・費用)
3. **万が一シナリオ**(遺族年金・死亡保険金・必要保障額分析)
4. **iDeCo / NISA / 証券口座**(運用利回り・非課税枠・受取時課税)
5. **保険設定**(生命保険・医療保険、解約返戻金)
6. **産休・育休**(出産手当金・育児休業給付金・社保免除)
7. **プラン比較**(複数シナリオの並列表示)
8. **モンテカルロシミュレーション**(運用リターンの確率分布)
9. **不動産**(自宅の固定資産税、投資用不動産の収支・減価償却)
10. **児童手当・各種給付金**の精緻化
11. **帳票出力**(PDF/CSV/Excelエクスポート。FP-UNIVはExcel出力を標準装備)
12. **税制改正ウォッチャー**(AIによる改正情報収集→パラメータ差分PRの自動生成、§9.4)

### 4.3 対象外(明示的にやらないこと)

- 確定申告に耐える厳密な税額計算(免責事項として明記、§12)
- マルチテナントの商用サービス化(料金プラン、決済、顧客管理)
- アプリ内AIアシスタント(= MCP経由で外部のAIがその役割を担うため、重複実装しない)
- 金融機関・証券口座とのAPI自動連携

## 6. 機能要件

### 6.1 データ入力(UI)

- FP-UNIVのQ1〜Q11に倣った**ウィザード形式の段階的入力**(ただしMVPは対象セクションのみ)
- 入力途中保存、再開可能
- 入力項目にはヘルプテキストと、MCP経由でAIが「この項目は何を入れるべきか」を案内できるメタデータを付与
- 入力データのJSONエクスポート/インポート(バックアップ・身内への共有・AIによる一括編集用)

### 6.2 計算エンジン

- **純粋関数群**として実装(DB・時刻・乱数に依存しない。入力と適用日パラメータから出力が一意に決まる)
- 計算は**月単位**。年末調整(12月)・住民税徴収開始(6月)・保険料率改定(4月/9月)等の「制度のカレンダー」を正確にモデル化
- **計算トレーサビリティ**:すべての出力金額に対し「どのパラメータのどの値を、どの式に適用したか」の根拠ツリーを生成可能にする(FP-UNIVにない差別化機能、AIによる説明の土台)
- シミュレーション期間:現在〜世帯主100歳(設定変更可)

### 6.3 税制パラメータ管理

詳細は §9。要点:

- 全数値をYAMLで管理(コードに数値を書かない)
- 各パラメータは `適用開始日` と `出典URL(根拠法令)` を必須属性に持つ
- 計算日に応じて有効なパラメータを自動選択

### 6.4 出力(UI)

- 年次サマリ表(収入/支出/税/社保/手取り/残高)+ 月次ドリルダウン。**表示粒度(月/年)切替と表示範囲(1年/3年/5年/10年/全期間)の切替**(FP-UNIV準拠)
- 貯蓄残高推移グラフ(ライブラリ:Chart.js または Plotly、軽量なものを選定)。**フロー(収入計/支出計/内訳)とストック(貯蓄残高/ローン残高)の2軸グラフ構成**(FP-UNIV準拠)
- 前提条件(物価上昇率・運用利回り等)の表示と変更UI。デフォルトは0%(FP-UNIVの思想)だが、参考プリセット(保守的/標準等)も選択肢として用意し、各数値の根拠・出典を併記する
- 残高枯渇・赤字年のアラート表示

### 6.5 MCPサーバー機能

FastAPIアプリ内にMCPエンドポイント(Streamable HTTP)を同居させ、同一の計算エンジン・DBを参照する。

**MCPツール(案)**:

| ツール | 概要 |
|---|---|
| `list_households` / `get_household` | 世帯一覧・詳細の参照 |
| `update_household` | 世帯情報の作成・更新 |
| `list_plans` / `get_plan` / `create_plan` / `update_plan` | ライフプランのCRUD |
| `run_simulation` | プランのシミュレーション実行(結果サマリを返却) |
| `get_cashflow` | 指定期間のキャッシュフロー明細(月次/年次)を取得 |
| `explain_amount` | 特定の金額(例:「2035年4月の住民税」)の計算根拠ツリーを返す |
| `list_tax_parameters` / `get_tax_parameter` | 税制パラメータと出典の参照 |
| `propose_parameter_update` | 税制改正に基づくパラメータ変更案の作成(人間の承認フローに載せる) |
| `compare_scenarios` | (将来)パラメータ差分や条件差分のシナリオ比較 |

- MCP経由の書き込み操作は、世帯データ変更時に**変更前スナップショットを自動保存**し、ロールバック可能にする(AIの誤操作対策)

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| 精度 | 年金・税・社保の計算結果は、公式の計算例(国税庁・日本年金機構の公表値)との照合テストで検証する。目標:概算でなく制度計算として一致 |
| 性能 | 1プランの全期間(約70年×12ヶ月)シミュレーションが3秒以内 |
| 可用性 | 身内向けのためSLAは設けない。Cloud Runの自動復旧に依存 |
| 保守性 | 数値の変更(税率等)はYAML編集のみで完璧に完結すること。構造的制度変更(新控除創設等)はコード改修を許容 |
| 検証性 | 税制改正のたびに回帰テスト(ゴールデンマスタ)で既存ケースへの影響を自動検知(§9.3) |
| 再現性 | 「いつ時点の制度で、どのパラメータ版で計算したか」を結果に記録(パラメータのGitコミットハッシュ等) |
| 移植性 | 入力データ・パラメータ・計算結果をJSON/CSVでエクスポート可能(サービス停止時もデータを残せる) |

## 8. アーキテクチャ

```
┌────────────────────────── Cloud Run (1コンテナ, max-instances=1) ─┐
│  FastAPI アプリ                                                    │
│  ├─ Web UI (Jinja2 + HTMX + Chart.js)      ← IAP認証               │
│  ├─ MCP エンドポイント (Streamable HTTP)   ← APIキー認証(※)        │
│  ├─ 計算エンジン (純粋関数モジュール)                               │
│  ├─ 税制パラメータローダー (YAML → 適用日で解決)                    │
│  └─ SQLite (永続化)                                                │
└────────────────────────────────────────────────────────────────────┘
        │ Litestream(継続レプリケーション)
        ▼
   Cloud Storage (バックアップ)      ※ MCP用認証方式は §11.3 の要検証事項

税制パラメータYAML: Gitリポジトリ管理(アプリはコンテナビルド時に同梱 or GCSから取得)
```

**技術スタック:**

| 層 | 選定 | 理由 |
|---|---|---|
| 言語/FW | Python 3.12+ / FastAPI | 本人がメンテ可能。型ヒント+pydanticで制度ロジックを安全に記述 |
| UI | Jinja2 + HTMX | サーバーサイド中心で実装コスト最小。SPAの複雑さを回避 |
| グラフ | Chart.js(CDN) | 軽量・依存なし |
| DB | SQLite + Litestream → GCS | コストほぼゼロ。身内向けの微小データに十分 |
| 認証 | IAP(Cloud Run) | 身内のGoogleアカウントのみ許可。アプリ側の認証実装が不要 |
| MCP | MCP Python SDK (Streamable HTTP transport) | FastAPIと同居可能 |
| IaC/デプロイ | Terraform または gcloud スクリプト + Cloud Build | 再現可能なデプロイ |
| テスト | pytest(回帰テスト含む) | 制度計算の検証基盤 |

## 9. 税制変更耐性の設計(方式A詳細)

### 9.1 パラメータYAMLの構造(イメージ)

```yaml
# parameters/income_tax.yaml
- path: 所得税.基礎控除.控除額
  description: 所得税の基礎控除額(合計所得2,400万円以下の場合)
  values:
    - from: 2020-01-01
      value: 480000
      source: https://www.nta.go.jp/taxes/shiraberu/taxanswer/shotoku/1199.htm
    - from: 2013-01-01
      value: 380000
      source: ...
```

- ディレクトリは制度分野別(income_tax / resident_tax / social_insurance / pension / child_allowance ...)
- 計算エンジンは `get_param("所得税.基礎控除.控除額", date)` で解決
- **コード中に税率・控除額・料率を直接書くことを禁止**(リンターで検査するルール化を検討)

### 9.2 構造変更への対応方針

| 変更の種類 | 対応 |
|---|---|
| 数値変更(税率・控除額・料率・閾値) | YAMLに時系列エントリ追加のみ |
| 計算式の係数変更(定率減税等) | YAML + エンジンの式参照箇所の確認 |
| 構造的変更(新控除創設、制度統廃合) | エンジンのコード改修(計算関数の追加)。変更箇所を局所化するため、制度分野ごとにモジュール分割 |

### 9.3 回帰テスト(ゴールデンマスタ)

- 代表的な世帯モデル(会社員単身、夫婦+子2人、自営業、年金受給者等)をテストフィクスチャとして保持
- 各制度改正の前後で「同じ入力→同じ結果(改正の影響がない項目)」を自動検証
- 公式の計算例(国税庁の源泉徴収税額表の例、ねんきん定期便のモデルケース等)を期待値として固定

### 9.4 税制改正ウォッチャー(将来拡張・MCP活用)

AIエージェントが国税庁・厚労省等の改正情報を調査 → `propose_parameter_update` でパラメータYAMLの差分案を作成 → Git PRとして提示 → 人間がレビュー・マージ、という運用フローを将来実装する。方式Aの「YAMLがGit管理されている」性質が、このAI協調ワークフローと自然に噛み合う。

## 10. データ設計方針

### 10.1 主要エンティティ(概念)

```
世帯 Household ─┬─ 家族成员 Member(生年月日/続柄/属性)
                ├─ 収入 Income(種別/金額/期間/上昇率)
                ├─ 年金加入記録 PensionRecord
                ├─ 支出 Expense(生活費/イベント支出)
                ├─ 資産口座 Account(種別/残高/金利)
                └─ ライフプラン Plan(前提条件セット)
                     └─ シミュレーション結果 Result(パラメータ版を記録)
```

- ライフプランとシミュレーション結果は分離(結果は再計算可能なキャッシュとしつつ、計算時のパラメータ版を記録)
- MCP/AIによる変更履歴を `audit_log` テーブルに記録(誰が・いつ・何を変更したか)

### 10.2 金額の扱い

- 金額は整数(円)で保持。計算中の端数処理ルール(切捨/切上/四捨五入)は制度ごとに法令通り定義し、パラメータYAMLで指定可能にする

## 11. セキュリティ・プライバシー

### 11.1 認証・認可

- Web UI: **IAP**でGoogleアカウント認証。許可リストに身内のアドレスのみ登録
- IAPのヘッダ(`x-goog-authenticated-user-email`)でユーザーを識別し、**自分の世帯データのみ**アクセス可能とする認可チェックをアプリ側にも実装(IAPは「入場制限」であり、データアクセス制御は別途必要)

### 11.2 データ保護

- 通信: HTTPS(Cloud Run標準)
- 保存: GCSバックアップは非公開バケット。個人情報・資産情報を扱う旨を利用者(身内)に明示
- リージョン: 東京(asia-northeast1)

### 11.3 要検証事項(Cloud Run採用の懸念点と対策)

| 懸念 | 内容 | 対策 |
|---|---|---|
| IAPの費用・構成 | IAPをHTTPSロードバランサ経由で有効化する構成だとLB料金(月約2,500円〜)が発生する。Cloud RunへのIAP直接適用(追加費用なし)が利用可能か要検証 | LB必須なら Identity Platform(Firebase Auth)での自前認証に切替検討 |
| Litestream運用 | max-instances=1 でSQLiteの同時書き込み競合を回避。リストア手順をrunbook化 | 定期リストア訓練(四半期に1回) |
| MCPの認証 | IAPはブラウザ向け。MCPクライアント(AI)からのアクセスは別経路(APIキー or OAuth)が必要 | MCPエンドポイントはIAP bypass + 独自認証で保護 |

## 14. 多角的・メタ的視点からの提案(FP-UNIVを超える+α)

ヒアリングで決定した内容に加え、設計上の強みとして以下を提案する。

### 14.1 計算トレーサビリティ(「なぜこの金額か」の説明可能性)

すべての金額に根拠ツリーを持たせ、`explain_amount` MCPツールでAIが「この住民税は、前年の所得○円にパラメータX(出典URL付き)を適用して…」と説明できる。**ブラックボックスでないことが、個人利用ツールとして最大の信頼性向上策**であり、FP-UNIVにもない差別化になる。

### 14.2 仮説シナリオ機能(税制変更耐性設計の副産物)

「消費税が15%になったら?」「基礎控除が縮小されたら?」という**将来の制度改正仮説をパラメータ差分としてシミュレーション**できる。パラメータが時系列YAMLで完全に分離されているため、ほぼ無料で実現できる(§4.2 の `compare_scenarios`)。

### 14.3 AIネイティブの割り切り

アプリ内AIアシスタント(FP-UNIVの「入力おまかせ」相当)は**実装しない**。MCP経由でClaude等がその役割を担うため、実装・運用コストを削減しつつ同等以上の体験が得られる。むしろ「AIが正しく操作できること」(ツールの命名、エラーメッセージの質、入力項目メタデータ)を設計品質として重視する。

### 14.4 パラメータの出典必須化と監査

数値の根拠URLを必須属性にすることで、(1)改正時に「どの数値が影響を受けるか」を出典から逆引きできる、(2)AIが数値の妥当性を一次情報に照合できる。

### 14.5 データポータビリティと退場設計

入力データ(JSON)+パラメータ(YAML)+結果(CSV)をすべてエクスポート可能にし、**サービスを畳んでも計算を再現できる**状態を保つ。個人の数十年分のライフプランを預かるシステムの誠実性として重要。

### 14.6 前提条件の完全な可視化

FP-UNIVの思想(デフォルト0%・恣意的係数なし)を継承しつつ、**すべての前提条件(物価上昇率・給与上昇率・運用利回り・制度パラメータ版)を結果画面に常時表示**する。比較ソフトの「1億円差」問題は前提条件の不透明さが原因であり、透明性は最大の防御。

### 14.7 月次エンジン×年次UIのUX設計

計算は月次でも、人間がまず見たいのは年次サマリ。年次表→気になる年だけ月次ドリルダウン、という情報設計にし、月次の詳細はMCP経由でAIに聞く導線も用意する。

### 14.8 検証スイートを「資産」として育てる

国税庁の税額表・ねんきん定期便モデル・自分の実縦値(給与明細との照合)をテストとして蓄積する。制度改正のたびにこのスイートが「影響検知ネット」として機能し、改正対応の心理的コストを下げる。

### 14.9 命名・ドメイン用語の法令準拠

内部の変数名・項目名は法令用語(「標準報酬月額」「退職所得控除」等)に揃える。制度調査時の認識齟齬とAIの誤解を防ぐ。

### 14.10 社保種別を「収入種別」に紐付ける入力モデル

FP-UNIVのQ2では、収入を「給与(厚生年金)/役員報酬(厚生年金)/役員報酬(国民年金・国保)/給与(国民年金・国保)」の4区分で入力させ、**社会保険の加入区分を暗黙に決定**させている。これは「どの保険制度に加入しているか」をユーザーが意識せずに正しく入力できる優れた設計であり、MVPでも採用する。

### 14.11 「基準年」と「月初残高」のモデル化

FP-UNIVはプランごとに**基準年**(シミュレーション開始年)を設定し、資産残高は**月初残高**で入力する。これにより「いつ時点のデータか」が明確になり、毎年の見直し(ライフプランを「育てる」運用)に対応できる。本システムでも採用する。
